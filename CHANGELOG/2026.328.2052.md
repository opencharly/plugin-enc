# 2026.328.2052 — docs(enc): -allow_other under keep-id, what it costs, and why the pod is never root

## Summary

`.agents/skills/enc/SKILL.md` explained the two-level user namespace behind `-allow_other` but left the reader to infer the rule, the measurement and the cost. It now states all three, present tense:

**Why it is required.** No charly pod runs as container root (D-HW-10): the workload is the image user, and a unit with a bind mount runs under `--userns=keep-id`. During container mount setup crun runs as inner uid 0, which maps to a **subordinate host uid (524288)**, not the FUSE mount owner — FUSE's kernel check rejects it and the container does not start:

```
$ podman run --rm --userns=keep-id:uid=1000,gid=1000 --user 1000 \
    -v /tmp/enc-test/plain:/enc <image> true
crun: cannot stat `/enc`: Permission denied
```

With `-allow_other` the same run is the image user at uid 1000, writes into the volume, and the host file lands `1000:1000` — no chown, no privileged shape.

**What it costs.** While mounted, gocryptfs presents the plaintext's own modes and `-allow_other` makes them binding on every local uid: a `0755` plaintext directory is readable by any local user for as long as it is mounted, and gocryptfs 2.7 has no narrower flag. Keep plaintext modes restrictive (`0700`/`0600`); never relax them to make one non-owner work.

## How tested

Documentation-only change (one skill file). The two measurements the new text rests on were run on this host (podman 6.2.0, crun 1.31, rootless) against a scratch gocryptfs test directory — not the operator's vault: without `-allow_other` the container refuses to start with the message pasted above; with it, `id -u` is 1000 and the file created inside is `1000:1000` on the host. The keep-id mapping (`host subuid 524288` for the mount-setup uid) and the `user_allow_other` prerequisite were already stated by the skill and are unchanged.
